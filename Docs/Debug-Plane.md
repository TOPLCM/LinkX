# 调试控制面

> 开源的人一定会问：产品里有没有一个没人说的后门？有一个本机 HTTP 控制面，
> 但交付构建里没有它，而且它只能驱动生产路径本来就允许的动作。
> 这一篇说清它的边界、能做什么、怎么被构建门控排除，以及怎么自证交付产物里没有它。

## 1. 它是什么、为什么存在

配对能不能成、大文件逐字节对不对、断线续传救没救回来，这些结论都要在两台真设备上反复确认。
靠人点鼠标做不到规模化，所以做了一个只对本机开放的 HTTP 控制面，让脚本能驱动同一批动作。

它受三条约束。

- 能力只有三类：读运行期状态、触发既有生产命令、注入分块故障，没有第四类。
- 每个动作都只是把命令投递到界面点击所走的同一条路径上，绝不另造一套逻辑。
  否则「控制面跑绿而交付版跑不通」就是假验证。
  `Platforms/Windows/src/app.rs` 的动作分派处有对应注释，这是代码约束，不只是文档口号。
- 相关代码全在 `agent-debug` 特性开关之内，默认构建不会带上它。

## 2. 能看什么状态

能读到的都是运行期已经存在的东西，分几类：链路连接、配对与身份、文件任务、相册条目、
通知、剪贴板、内部计数器。

## 3. 能触发哪几类动作

动作分四类：连接与解绑、SAS 核对的确认与拒绝、对端身份变化提示的接受与拒绝、
内容与状态的下发（文件发送与取消、相册翻页与导出、功能开关、媒体指令、剪贴板、实例重启）。
故障注入只有两类：发送端丢掉指定序号的分块、入站把指定序号的分块当作没收到，都只生效一次。

这里不列具体请求路径与参数：这个面不属于交付版，把它写成操作手册只会误导读者。
要用就读 `Crates/debugd/src/lib.rs` 和两端 `agent-debug` 的分派块，代码就在仓库里。

有两点值得单独说清。「确认 SAS」只是按下按钮，不会替系统跳过核对。
功能开关的参数写错一律报错，不给默认值。

## 4. 边界：它能碰到谁

- 只绑 `127.0.0.1`，绝不监听 `0.0.0.0`；端口见 `Crates/debugd/src/lib.rs` 的 `DEFAULT_PORT`。
- 浏览器发起的请求一律 403：`Host` 不是回环名、带 `Origin` 或 `Referer`、
  `Sec-Fetch-Site` 不是 `none`，这三种形状都拒。
- 无鉴权，靠「只绑回环 + 不接受浏览器发起」这两条边界成立。
- 能做的只有产品界面本来就能做的事，加上故障注入。**不能**导出会话密钥、跳过 SAS 核对、
  伪造已配对身份、连到任意远端主机、执行任意命令。
- 路由是固定枚举，不在枚举里的路径（包括 `../../Windows/System32` 这类拼接）返回 404。
- 只存在于开发与验收环节。日常装机用的是 release 构建，没有这个监听。

**为什么「只绑 127.0.0.1」还不够**：DNS 重绑能让一个恶意域名解析到 `127.0.0.1`，
于是浏览器发出去的请求看起来就是本机自己发的。真到那一步，状态读取能把 SAS 与双端指纹拿走，
而「确认 SAS」这类动作是不触发 CORS 预检的简单请求，等于替用户点掉那道防中间人确认。
所以才有上面那条「浏览器发起一律 403」，并有两条对照测试守着：本机脚本必须放行，
浏览器形状必须被拒。

**同一台机器上的任意本地进程都能驱动它**：这个控制面没有鉴权，这正是它绝不能进入交付构建的原因之一。
在多用户机器或不可信的本地环境里用，先把它关掉——不启用 `agent-debug` 特性，就根本没有这个监听。

手机端同样只在回环上监听。从电脑端访问走 `adb forward`：由 adb 在电脑端开一条到设备的隧道，
而不是让手机开放端口。之所以只对这台机器的回环开放，就是因为上面这些能力一旦能被别人碰到，
它就不再是调试工具，而是远程操控。

## 5. 构建门控

`agent-debug` 是一个可选 cargo 特性。Windows 壳在 `Platforms/Windows/Cargo.toml` 里声明它，
手机端核心 `.so` 用同名特性，由 `Scripts/build-android-core.sh` 的 `DEBUGD=1` 决定是否加上。
交付路径默认不含它：`bash Scripts/build-msi-windows.sh` 与
`bash Scripts/build-android-apk.sh --release` 出来的包都没有这个监听。调试变体才显式加上特性，
并且不打 MSI。

安卓侧的 `DEBUGD=1` 要同时给 `build-android-core.sh` 和 `build-android-apk.sh`。
APK 脚本会校验 `.so` 里的状态并强制重建，只给前者会产出一个名字叫 debug、里面没有控制面的包。

调试包与交付包用同一把签名。这把密钥由出包脚本在构建机器上自行生成并复用，**不随仓库分发**，
所以你在自己机器上打出来的包，哈希与 [`../Release/README.md`](../Release/README.md) 登记的那份
对不上是正常的，因为密钥不是同一把。同一把密钥的好处是覆盖安装不丢配对，
不必为了装调试包而重新配对一次。

## 6. 判据要从事件流来

界面文案不足以证明一次传输成功：任务行是按方向加文件名复用的，
「有文件了」「显示成功」都可能是假通过。驱动这个面的验收脚本因此只从事件流与落盘字节数比对得结论，
不读界面文案。自己写自动化时请沿用同一口径。

## 7. 怎么自证交付产物里没有它

```bash
bash Scripts/check-release-clean.sh
bash Scripts/check-release-clean.sh --apk-so <APK 路径>
```

做法是对产物字节直接断言，而不是相信「配置里说关了」：取产物的可打印串
（没有 `strings` 时退化为按字节筛），命中控制面符号或只在调试路径里出现的依赖即失败。
Android 那条会解出 `lib/arm64-v8a/liblinkx_core.so` 与 `classes.dex` 分别扫。
命中的模式列在脚本里，这里不复述，改一处就能同步。

同一份脚本还带一条反向断言：必须命中一个产品自己的符号，否则判定为扫错了文件或产物是旧的。
没有这条，「扫了个空文件所以全绿」就成了假通过。

要说清一层：字节扫描挡不住控制面被编进来。端口号是立即数、路由名是运行期拼接，
都不会以连续字面量出现在产物里。真正的闸门是依赖图——Windows 那条会跑 `cargo tree -e features`，
`linkx-debugd` 没进图，产物里就不可能有它。

Android 侧还有一处容易被误读：Kotlin 里那几个 `nativeDebug*` 声明必然留在 `classes.dex` 里，
它们是 JNI 入口、proguard 规则要求 keep，删不掉。决定成败的是 `.so` 里没有对应实现，
于是声明只剩死引用。所以这一层断言的是「跑不起来」，不是「名字不许出现」。

## 8. 不想用它就彻底去掉

能。`agent-debug` 是可选特性，交付路径默认不启用，上面那份脚本保证交付产物里没有可用的控制面。
从源码 `cargo build --release` 出来的东西就是这个状态，你可以自行跑一遍那两条命令验证。
