# 电脑端回复手机端通知

一句话：电脑看到手机通知时，如果那条通知的自家应用支持快速回复，就能在电脑上回一句话。

## 怎么工作

整条链路复用既有的通知同步，不新建第二套通知系统。

```text
手机通知栏
  │ NotificationListenerService.onNotificationPosted
  ▼
手机端采集 pkg / tag / id 与回复入口（首个挂了 RemoteInput 的 action 及其 resultKey）
  ▼ NOTIFY_PUSH 0x10
电脑端：can_reply 为真才画「回复」入口
  │ 点「回复」→ 顶部回复条 → 输入 → 发送或回车
  ▼ NOTIFY_REPLY 0x11
手机端：事件泵里只排队，在 reply 线程上按 pkg + tag + id 现找仍在通知栏的条目
  │ RemoteInput.addResultsToIntent → action.actionIntent.send
  ▼ NOTIFY_REPLY_ACK 0x13
电脑端：按 reply_id 对上号，显示「已发送」或手机端给的那句原因

（并行的一条）手机通知消失 → NOTIFY_DISMISS 0x12 → 电脑端只撤掉那一行的「回复」入口
```

有四个选择值得单独说。

**手机端不缓存通知对象。** 收到回复请求时按 `pkg`、`tag`、`id` 现找。缓存下来的 `PendingIntent`
在通知被划掉后就是废的，拿它回复只会静默失败，而静默失败是最要不得的形态。

**跨进程调用一律出锁。** `activeNotifications` 是 Binder 调用，而事件泵是同步的，
锁内执行会按住蓝牙分片、TCP 帧和所有 JNI。所以回复与媒体指令同构：只排队，
在 `linkx-reply` 自己的线程上执行。

**回执按 `reply_id` 对号，而不是按行号。** 新通知会插到列表最前，行号会漂。
对不上号的回执必须出声（「收到一条不认识的回执」），否则「手机端回了但电脑端没显示」
是最难查的一类问题。

**通知消失要出声。** 从通知里回完短信，短信应用会把那条通知自己清掉；电脑端若不知道，
下次点「回复」只会得到一句「这条通知已经不在了」。所以手机端对当初以 `can_reply=true`
转发过的条目额外报一条 `NOTIFY_DISMISS`，电脑端收到后只撤那一行的回复入口
（连正在编辑的输入框一起收掉），**行本身留着**——正文还能复制，
电脑上的「最近通知」不是通知栏的镜像。上报范围只限这几条，
是为了不在用户每划掉一条通知时都往蓝牙上塞一帧。

## 协议字段

| 消息 | 值 | 方向 | 说明 |
|---|---|---|---|
| `NOTIFY_PUSH` | `0x10` | 手机端 → 电脑端 | 原有通知转发，加了回复定位信息 |
| `NOTIFY_REPLY` | `0x11` | 电脑端 → 手机端 | 回复请求 |
| `NOTIFY_DISMISS` | `0x12` | 手机端 → 电脑端 | 通知消失上报 |
| `NOTIFY_REPLY_ACK` | `0x13` | 手机端 → 电脑端 | 回执，无论成败必回一条 |

`NotificationPush` 新增五个字段：`tag`、`notification_id`、`can_reply`、
`reply_action_index`、`reply_result_key`，原有字段一律不动。

`NotificationReply` 带 `reply_id`、`package`、`tag`、`notification_id`、`action_index`、
`result_key`、`text`。`NotificationReplyAck` 带 `reply_id`、`package`、`ok`、`error`，
其中 `error` 是手机端写好的、给用户看的一句原话，电脑端原样显示，不翻译也不吞掉。
`NotificationDismiss` 只带 `package`、`tag`、`notification_id`、`key_hash` 这些定位信息，
**不带任何正文**。

## 新旧版本混用

proto3 的未知字段会被忽略，未知消息类型只报错不断链，所以混用不会把链路搞坏。

- 新手机配老电脑：多出来的字段被忽略，通知照旧显示，只是没有回复入口。
- 老手机配新电脑：手机端回一句「未知业务消息类型」并且不给回执，电脑端靠 10 秒超时把这条回复
  判为「手机没有回应（请把手机端 LinkX 升到最新版）」，不会停在「点了没反应」。
  老手机也不会报消失，电脑端的入口就停在旧的「点了才知道没了」形态，不会更坏。

这几个字段不需要动帧版本，也不需要动产品版本号。

## 为什么只用 RemoteInput

模拟点击、无障碍服务、后台读剪贴板再注入文字，这几条路都不走。模拟点击与无障碍要的是
用户根本不该给一个传输工具的系统级权限，而且拿到之后能对任何应用动手；
后台读剪贴板受系统的输入焦点判据约束，第三方 App 没有通路。

这里只用 Android 官方为快速回复设计的组合：`NotificationListenerService` 加 `RemoteInput`。
它要的权限就是通知使用权，能做的事也只有「把一句话递进应用自己准备的回复框」。

## 支持范围与降级

**只有应用自己挂了 `RemoteInput` 的通知可以回复**，那是应用构建通知时的选择，不是本产品的能力。
界面上没有回复按钮就等于真的不支持，不留一个点了才报错的按钮。

- 实现了 Android 官方快速回复的应用（Telegram、WhatsApp、Slack、Gmail 这类）可以回复。
- 系统短信应用可以回复：验证码通知常挂 `RemoteInput`，电脑端发的字会真的进会话。
- 微信安卓端的通知预期不自挂 `RemoteInput`，因此预期不支持。
- 不带回复动作的通知（支付、游戏这类）不支持，也不显示入口；验证码类不在这一档里。
- 常驻通知（`isOngoing`）不转发，也就谈不上回复；敏感通知（`android.isSensitive`）正文不转发。

能不能回复完全由**那一条通知自己**决定：同一条短信在「刚收到」和「打开会话后」两种状态下
可以一边有、一边没有。所以判据只能是应用挂没挂 `RemoteInput`，不能按应用类型猜。

## 已知限制

- **通知必须在回复那一刻还在通知栏**。用户已经划掉、或应用自己把通知清掉（回完短信就清是常态），
  回执就是「这条通知已经不在了」。手机端会上报消失、电脑端随即撤掉入口，但两者之间总有一个
  链路往返的窗口，落在窗口里点仍会拿到那句原因。
- **一个 action 上有多个输入框时，只填点名的那一个**，其余留给应用自己处理。
- **回复正文与通知正文一样不进日志**，只记 `pkg`、`id`、`tag`、`key` 与长度。
- **配对是前提**。未配对时引擎直接拒发：这条会真的把文字送进对端某个应用，比播放指令更硬。
- **电脑端回复框沿用自绘输入的既有限制**：只应答 `WM_CHAR` 与 `Backspace`、`Enter`，
  没有光标定位、选区与粘贴。
- **手机端排队上限 8 条**，超了就回「回复太频繁」。
