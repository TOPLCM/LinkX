# 安全与隐私口径

> 这份文档回答社区最常问的三件事：数据从哪走、谁能在中间看到、产品里有没有后门。
> 调试控制面那部分单独写在 [`Debug-Plane.md`](Debug-Plane.md)。

## 数据路径

LinkX 是**纯局域网 P2P**：没有账号、没有服务器、没有云端中转。手机与电脑必须在同一个
局域网（或同一台机器的蓝牙范围内）。全仓无遥测、无更新检查、无硬编码远端地址。

| 用途 | 走哪条通道 | 是否加密 |
|---|---|---|
| 设备发现 | 蓝牙广播 / UDP 55676 信标 | 明文（只含设备名与协议版本，不含身份密钥） |
| 配对与握手 | 蓝牙 GATT | Noise XX 握手 |
| 通知、剪贴板、媒体指令、电量 | 蓝牙 GATT | 配对后逐帧 AEAD |
| 文件与相册原图 | 局域网 TCP（小文件可走蓝牙兜底） | 配对后逐帧 AEAD，逐块 CRC32 + 整文件 SHA-256 |

通道分工是设计约束而不是实现细节：大文件不会因为蓝牙掉线而偷偷降级，它会明确报错。

## 信任模型

- **信任锚是 RSA-2048 指纹**，不是 MAC 地址、不是设备名。地址漂移、改名都不影响身份。
- 首次配对时两端各显示一组 6 位短鉴密词（SAS），**人工核对一致**才写入信任库（TOFU）。
- 对端身份变化（重装系统、换机导致指纹漂移）一定停下来要求再次人工确认；
  自动重连只放行"指纹命中已落库设备"的连接 —— **自动重连 ≠ 自动信任**。
- 换绑/解绑在两端各自本地执行，不存在"远端撤销"这种能力。

## 加密实现

- 握手用 `snow`（Noise 协议框架）+ 自定义套件解析器：ChaCha20-Poly1305 / X25519 / SHA-256。
- 会话密钥由握手派生，逐帧 AEAD，方向域分离的 nonce；接收侧有抗重放滑动窗口
  （心跳与业务帧各用一份窗口，避免一类帧把另一类的窗口顶满）。
- 身份签名用 RSA-2048（PKCS#1 v1.5），验签前强制模长 2048 位、签名 256 字节。
- **依赖 `rsa` 0.9.10 挂着一条永不修复的通告，这里是书面决策**：RUSTSEC-2023-0071
  （Marvin，5.9 中危，`patched = []`，上游没有修复版本）。该通告的适用条件是"攻击者能观测到
  本机 RSA **解密**的时序"。LinkX 对 RSA 只有两个用法：`sign_binding()`（本机私钥签名，
  确定性操作）与 `verify_binding()`（拿对端公钥验签，不碰本机私钥），**全程不做 RSA 解密**，
  因此不存在可被查询的填充预言机。判定：实际不可利用。复核日期 2026-10-02；一旦本项目出现
  任何"用本机私钥解对端送来的字节"的用法，这条决策立即作废重评。
- **依赖安全通告有门禁**：CI 的 `supply-chain` job 跑 `cargo audit`，主 workspace 与
  `Tests/fuzz` 两份 `Cargo.lock` 都扫。上面那条 `rsa` 通告以 `--ignore RUSTSEC-2023-0071`
  放行，理由就是本节这段书面决策——**要放行一条必须在 CI 参数里写出编号，同时在这里留下原因**，
  不许静默忽略。本机实测（2026-10-02）：不加 `--ignore` 时这条门禁确实报
  `error: 1 vulnerability found!`（只有 `rsa` 这一条，160 个依赖），加上就全绿 ——
  门禁能开火是演过的，不是假设的。
- 门禁 `Scripts/check-crypto-audit.sh` 做的是**密码学选型策略**：依赖图里混进 AES 系实现
  （本项目只允许 ChaCha20-Poly1305 一条 AEAD 路径）即违规，同时要求 ChaCha20-Poly1305 /
  X25519 / SHA-2 / HKDF 必须在位。**它不查安全通告**，别把它的名字当成"依赖漏洞有人管"。
  **改这条口径要连门禁一起改**，不要绕过它。

## 输入一律不可信

- **接收侧文件名净化（两端是两套实现，故意不同）**：Windows 侧改写为 NTFS 合法名 ——
  非法字符、保留设备名、控制字符、超长截断、`.`/`..` 与绝对路径成分剥离，实现与出处见
  `Crates/transfer/src/filename.rs`（移植自 LocalSend，Apache-2.0）。**安卓侧不经过这个文件**，
  走 Kotlin 自己的 `sanitize()`（`LinkxRuntime.kt`）：`<>:"\|?*` 在 ext4 与 MediaStore 上是合法
  文件名字符，照抄 Windows 那张表只会把用户本该看到的名字改坏。两端的**共同不变量**只有三条：
  落盘名必须单段、不可穿越、字节数有界。采取"改名式"而不是拒收。
- **发送侧同口径校验**：本机文件名不合规时先拒发并说明原因，避免"发出去了对方收到个怪名字"。
- **协议解析**：帧头、TLV、protobuf 三个入口都有 fuzz 目标（`Tests/fuzz/`），
  崩溃样本会进 CI 的 artifacts 目录。
- **接收上限**：单帧 1 MiB（这个值是**未认证输入直接决定的分配大小**，收到 8 MiB 只是把攻击面
  放大八倍、换不到任何合法能力）、单文件 4 GiB、剪贴板正文 32 KB（两端同口径，超了拒收/拒发并
  出声，不截断）、落地文件名长度、缩略图缓存字节数、蓝牙并发分组与局域网对端表条目数都有硬上限，
  防止"对端声明一个天文数字，然后慢慢写满你"。

## 本机调试控制面（交付版里没有它）

调试构建带一个只绑 `127.0.0.1` 的 HTTP 控制面，用来让自动化脚本驱动真机验收。
它的边界、能力清单、构建门控，以及**如何自己验证交付产物里不含它**，全部写在
[`Debug-Plane.md`](Debug-Plane.md)。一句话版：

- 只绑回环，且拒绝浏览器发起的请求（DNS 重绑那条路已经堵上）；
- 由 cargo feature `agent-debug` 门控，**交付构建不启用即完全不参与编译**；
- `Scripts/check-release-clean.sh` 对 exe 与 APK 内的 `.so`/`classes.dex` 做字节级取证。

## 已知会被 ROM 削掉的能力

这些不是漏洞，是平台边界，产品选择如实降级而不是假装成功：

- 安卓后台读取剪贴板（AOSP 只允许持有输入焦点的应用读）；
- 息屏后的后台存活（多数 ROM 会杀后台服务）；
- 通知监听可能被 ROM 的"自启动优化"回收，回收后系统不再绑定监听服务；
- 从相册导出的媒体可能被平台就地脱敏（定位/部分 EXIF 字段被写 0）。

细节与用户侧恢复办法见 [`../README.md`](../README.md) 的「诚实的边界」与
`CHANGELOG.md` 的已知限制条目。

## 漏洞披露

涉及安全的问题（尤其是配对、加密、文件名处理路径）请走私有渠道联系维护者，
**不要在公开 issue 里贴可复现的利用细节**。其余问题 —— 跑不通的构建、假成功的验收、
静默失败 —— 都算 bug，直接开 issue。
