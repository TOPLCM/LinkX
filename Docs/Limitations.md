# 已知限制（不粉饰）

产品视角的短版在 [`../README.md`](../README.md) 的「诚实的边界」。这里放完整口径与原因，
一条一条说清"是什么表现、为什么、能做什么"。

## 平台与 ROM 削掉的能力

- **安卓后台读剪贴板**：AOSP 只允许持有输入焦点的应用读剪贴板，第三方 App 无法绕过。
  LinkX 的做法是如实降级 + 提供手动「立即同步」，而不是假装成功。
- **电脑回复手机通知，只对"应用自己开了口子"的通知有效**：回复走 Android 官方的
  `RemoteInput` —— 应用做通知时挂了快速回复按钮，我们才能把文字递进去（短信已真机验过会挂，
  Telegram / Gmail 这类按机制也挂；微信安卓端预期不挂，尚未实测）。没挂的通知在电脑上
  **不显示回复入口**，这不是我们没做。
  另外通知必须在回复那一刻还在通知栏：回完短信应用常会把通知自己清掉，现在手机会上报消失、
  电脑随即撤掉那个入口；但"消失"到"电脑收到上报"之间有一个链路往返的窗口，落在窗口里点
  仍会拿到那句"这条通知已经不在了"。详见 [`NOTIFY_REPLY_DESIGN.md`](NOTIFY_REPLY_DESIGN.md)。
- **息屏后失去控制**：多数 ROM 会杀掉后台服务。设置页里有明确的保活入口和说明，
  但根因在系统侧，不在这里。
- **通知同步依赖系统"把监听服务绑回来"，这一步在部分 ROM 上要用户授权一次**：转发依赖
  `NotificationListenerService` 被系统绑定。**实测（HyperOS，红米 Note 11T Pro）**：
  应用进程被系统结束之后，`enabled_notification_listeners` 里我们那一条**仍然在**，
  但系统默认不再重新绑定 —— 表现就是"权限明明开着、电脑一条通知都收不到"。
  我们做了三件事：① 启动与解绑回调里调 `NotificationListenerService.requestRebind()`
  （这台 ROM 收下请求但不绑定，只对 AOSP 类设备有效，**不当它作保证**）；
  ② 进程只要活着就自动开始蓝牙广播（开机广播、覆盖安装、系统重新绑定监听三处都挂），
  否则"App 被救活了、电脑拨不回来"；③ 安卓「通知」页**如实区分三种状态**：未授权 /
  已授权且生效 / **已授权但系统当前没有把通知交给我们**，并给两个入口 ——
  **允许自启动**（直达各厂商 ROM 的自启动管理页）与重新开启通知使用权。
  **实测：允许自启动之后，杀掉 App 几秒内系统就自行重新绑定并恢复投递，不需要再碰开关**；
  没允许的话，恢复动作只能由用户在设置里把开关关掉再打开一次，客户端无法代授权。
- **链路重建期间，电脑端的「已配对」可能先于真实连通显示几十秒**：手机进程被结束后，
  手机侧会重发自我介绍触发重新握手；这一步在个别时序下会来回两三拍（实测约 20 秒一轮），
  期间电脑仍显示「已配对」。**这期间到达的通知不会丢** —— 链路恢复时会把仍在通知栏里的
  条目补发一遍（实测：断链窗口里投的一条，最迟 30 秒后自己到了电脑，全程无人操作）。
- **只同步新鲜窗口（10 分钟）内的通知**：系统在监听绑定的瞬间会把整栏通知补投一遍
  （实测一次 35 条），全转会把蓝牙"单片在途"的发送队列打爆 —— 超限时丢的恰是最旧的，
  真正该到的那条反而到不了电脑。躺在栏里几天的旧通知也不该当成新事件同步。
- **从相册导出的原图/视频可能"差几十字节"**：Android 在第三方 App 读取媒体文件时会
  **就地脱敏**（照片 EXIF 的部分字段、视频 `udta` 里的 `©xyz` 定位框被写成 0，
  **长度不变、内容变**）。因此导出结果与手机本体上的文件在这几十字节上可能不同 ——
  这不是链路传坏，也不是本产品在改写：两端算的是同一份被脱敏的流，所以逐块 CRC 与
  整文件摘要都对得上。要拿到未脱敏原件需要申请 `ACCESS_MEDIA_LOCATION`
  （一个定位类敏感权限），本产品**没有**申请，宁缺毋滥。
  我们的验收口径因此是：**逐字节比对拿 `adb pull` 下来的原件比，不拿 App 读到的比**。
- **BLE 广播携带系统蓝牙名**：电脑侧的设备列表与「自动连接已绑定设备」都**按名字认领**，
  名字只在配对后的加密通道里给就永远来不及（0.5.0 曾试着把名字从广播里去掉，结果自动重连
  认领不到手机、列表里全是无名项，已回退）。介意的人请在系统蓝牙设置里把设备名改成中性名，
  本产品不自造另一个常发标识符 —— 那只会把一个可见名字换成一个更可跟踪的常量。

## 传输与容量边界

- **单文件接收上限 4 GiB**：超过就以界面提示 + 回执明确拒绝（"文件超过本机接收上限"），
  不会静默截断，也不会假装收完。要传更大的文件请先分卷；上限存在的理由是接收侧落盘与
  续传索引的边界，抬它之前要先改协议里的长度口径。
- **断点续传要两端都升级**：0.4.5 起「迟到的续传请求」能被救回，但修复跨两端与协议层；
  **新电脑配旧手机时，那条路径会以超时明确失败，不会假成功**。
- **文件名校验与路径穿越防护**在发送侧与接收侧同口径执行，但对端版本过旧时会被拒绝
  而不是被纠正。
- **HyperOS/MIUI 等 ROM 会拒绝把「下载」目录授权给第三方应用**，建议选「文档」。

## 交互与体验

- **自动重连在电脑侧**：0.5.0 起，电脑上的 LinkX 会在两种情况下自己找回已绑定设备 ——
  进程刚启动（手机还在解锁），以及**掉线超过 30 s、自愈放弃之后**（手机被杀、装进口袋
  一小时再回来）。设置页开关「自动连接已绑定设备」默认开，关掉即回到每次都要人点一次设备行。
  两条边界：① 前提是电脑上有 LinkX 在跑 —— 装机时的「Run at logon」组件（`HKCU\...\Run`）
  负责这件事；② **自动重连 ≠ 自动信任**，只有对端 RSA 指纹命中已落库的设备才静默放行。
  手机是 BLE Peripheral：打开 App 即在广播、由电脑拨过来，因此手机上没有这个开关。
- **相册拖出（0.5.0 的交互）**：单击一格 → 格子正中出现进度环与百分比（**可以松手，不用按住**）
  → 环跑满后左上角标「可拖出」→ 拖到资源管理器/微信即一次到位；连着选几张，
  从任意一格拖出去会把选中的这一批一起带上（没跑完的会补齐并说明）。
  载荷是 shell 认的 `CF_HDROP`，因此要求原图**先完整落到本机临时目录**
  （保留数有软/硬上限，退出时清扫）。我们试过改成"松手后才传字节"的拉模型
  （`FileContents`/`IStream`），字节比对全过但真机上会卡界面 ——
  资源管理器是在 UI 线程的模态拖放循环里**同步**读字节的，要做对得把数据对象搬到独立线程
  并实现异步流语义，因此本版撤回。
- **没做的能力**：屏幕镜像、通话、应用流转、键鼠共享（协议位有预留的写明预留，未实现）；
  随机播放/单曲循环（安卓没有通用的切循环指令，接上去只会是个点了没反应的假按钮）。

## 交付与签名

- APK 用仓库内自签测试密钥签名（`Tools/Keys/linkx-test.jks`，缺失时脚本生成）。
  正式分发请用你自己的 keystore 重签，见 [`Build.md`](Build.md)。
- MSI 未做代码签名，首次运行会有 SmartScreen 提示（「更多信息 → 仍要运行」）。
- Windows 端只在 `x86_64-pc-windows-gnu` 目标下嵌入图标资源；msvc 构建没有图标，
  不要拿它交付。
