# Release 目录约定

这里是交付物出口，不是源码。**当前版本的二进制不入库**（走 Releases 页面分发），
**已退役版本连包带校验值一起归档在 `Archive/`**，克隆仓库就能取到那一代的原包。
`.gitignore` 排除了 `Release/Windows/*`、`Release/Android/*`、`Release/Debug/*`
与 `Release/Archive/**/LinkX-*.idsig`（后者是签名中间件，用户用不上）。

```text
Release/                          （Windows/、Android/、Debug/ 是本机产物、不入库；Archive/ 入库）
  Windows/LinkX-<版本>-x64.msi              当前版本：电脑端安装包，传统 64 位（+ .sha256）
  Windows/LinkX-<版本>-arm64.msi            当前版本：电脑端安装包，ARM64 原生（+ .sha256）
  Android/LinkX-<版本>-release.apk          当前版本：手机端交付 APK（+ .sha256）
  Notes/v<版本>.md                          这一版对外的 Release 正文本身（发布流水线原样搬运）
  Debug/                                    调试包：不入库、不归档
  Archive/v<版本>/                          已退役版本，每版一层（本体 + .sha256 都在库里）
    Windows/LinkX-<版本>-x64.msi{,.sha256}
    Android/LinkX-<版本>-release.apk{,.sha256}
```

## 四条规则

1. **当前版本永远在 `Windows/` 与 `Android/`，且必须晚于最后一次代码改动**。
   产物比代码旧就不算交付。
2. **换版本时把上一版整体移入 `Archive/v<版本>/{Windows,Android}/`**，保留原始文件名与
   `.sha256`，不重命名、不重打包、不删，同时在 `Archive/00-README.md` 补登记一行。
   所有版本都用同一套分层。这一条以**上架**为触发，不是以出包为触发。
3. **调试构建（`*-debug.apk`）不归档、不分发**，移到 `Release/Debug/`。
4. **`Notes/v<版本>.md` 里放的就是 Release 正文本身**：首行固定 `v<版本>更新日志：`，之后一行一条
   「关键词：短句」，不写协议号、算法名、文件路径，也不堆长校验值（本表才是校验值的家）。
   发布流水线建草稿时原样搬运它，首行对不上就停下——对外的话由人写，机器不代笔。

## 当前线上版本 0.5.3（2026-11-02 上架）

**Releases 页现在发的是这三条附件**，由 GitHub Actions 从标签 `v0.5.3` 构建；下表三条哈希是
从公网下载地址回取到本机逐字节算出来的，下载后直接比对即可。
上一版 0.5.2 仍在页面上（历史条目不撤），归档按规则 2 以上架为触发：0.5.3 已上架，
`Archive/v0.5.3/` 要在这一轮建起来；0.5.2 已在它自己那一轮进过 `Archive/v0.5.2/`。

- **`LinkX-0.5.3-x64.msi`**：传统 64 位 Windows（Intel/AMD）。1,048,576 字节。
  这一版电脑端修了相册五处（缩略图卡"载入中…"、清单与原图等待没有结局、超量导出静默少发、
  多选拖出凑不齐、状态行读数），安装向导与其余功能与 0.5.2 一致。表级判据全过：`CloseApplication`
  （卸载/升级前先结束本体）、per-user 挂载与卸载清理、防火墙只有一条、`ProductVersion = 0.5.3`；
  包内 payload 由 `Scripts/check-msi-payload.ps1` 从包里取出来核过：1,222,656 字节、PE `0x8664`、
  与盘上刚编的那一份同哈希（旧判据只看构建目录里那份 exe，看不到包里装的是谁）。
- **`LinkX-0.5.3-arm64.msi`**：**原生 ARM64 包**（高通骁龙等 Windows on ARM 笔记本），1,003,520 字节。
  走的是另一条链：MSVC `aarch64-pc-windows-msvc` + Windows SDK 的 ARM64 库，图标资源由 SDK 的
  `rc.exe` 编（`build.rs` 两条链各自要求资源真的编进去，找不到就失败）。产物级判据：
  **包里的** `linkx.exe` 与 msvc 那份同哈希、PE 机器码 `0xAA64`、`.rsrc` 段非空、
  **不依赖 VC++ 可再发行组件**、卸载保护落的是 `Wix4UtilCA_A64`、`ProductVersion = 0.5.3`。
  ⚠ **运行期未在 ARM 真机实测**（手上没有 ARM 机器）：装得上吗、蓝牙能不能连、传输正不正常，
  都没有实测数据 —— 这一版能说的只有"包是对的"。
  这条包为什么值得做：x64 包在 ARM 电脑上要靠系统转译层跑，转译层自己吃内存也拖性能，
  且已有 ARM 用户反馈功能表现不对。
  两条与"能不能装上"直接相关的事实：① 这个包**不依赖 VC++ 可再发行组件**——MSVC 默认动态链
  `VCRUNTIME140.dll`，那是运行库、不是系统自带，没装它的 ARM 笔记本上 exe 连启动都起不来，
  而在 x64 宿主上编又测不出来；现在用 `+crt-static` 静态链，并由 `build-msvc-windows.sh`
  解析 PE 导入表拦住这类依赖。② 包里的本体由 `Scripts/check-msi-payload.ps1` 从包内解出来核过，
  与刚编出的那份同哈希、PE 机器码 `0xAA64`——以前这条判据不存在，光看构建目录里的 exe 不算数。
- **`LinkX-0.5.3-release.apk`**：**一个 APK 带两套 ABI** —— `lib/arm64-v8a/liblinkx_core.so`（910,576 字节）
  与 `lib/armeabi-v7a/liblinkx_core.so` 都在包里，系统按设备架构自动取用，32 位老机装得上。
  `versionCode` 15→16；签名证书与 0.5.2 同一把（SHA-256 `85a11f55…09a58e`），覆盖升级不丢配对。
  **上架那份（CI 构建）体积 3,001,997 字节**，内含 `arm64-v8a` 908,224 + `armeabi-v7a` 574,156；
  本机自构的那份是 3,032,014 字节（910,576 + 578,260）——同一条脚本、同一批门禁，字节随构建环境变，
  两件事核过才敢并列：签名身份相同、包内内容物一一对应。
  真机验收是在**本机那份**上做的：Redmi Note 11T Pro（Android 14）覆盖安装后未重新配对即回到已配对；
  这台机强制以 `armeabi-v7a` 跑同一个包（进程 `app_process32`）后，文件双向逐字节通过、2.5 GB 单文件两端哈希一致。

| 平台 | 文件 | 大小 (bytes) | SHA-256 |
|---|---|---|---|
| Windows | `LinkX-0.5.3-x64.msi` | 1,048,576 | `f260d23bd90cd5ef39059309fcfd6f2fbe606352beb76cb648382bac76fcf5c7` |
| Windows | `LinkX-0.5.3-arm64.msi` | 1,003,520 | `6352881714c22fb72f44000b0056fa6ce2ae2378d6f6c3e473e8dc40e48de267` |
| Android | `LinkX-0.5.3-release.apk` | 3,001,997 | `e1ef49868ce78b1bf02ca05077156ca6768f2935d68acfa34f2d9f1116fc078e` |

**上表是 Releases 页面上那三个文件**（由 GitHub Actions 从标签 `v0.5.3` 构建），下载后与这张表比对即可。
三条哈希都是把公网下载地址重新取回本机逐字节算出来的，不是抄构建日志。

⚠ **本版 APK 与本机自构的那份不是同一串字节**，这是预期而不是错误：APK 里的 `.so` 编进了源码行号、
dex 也随构建环境变，CI 那份是 3,001,997 字节、本机第四轮那份是 3,032,014 字节。两件事已经核过才敢这么写：
① 两份的签名证书 SHA-256 都是 `85a11f55…09a58e`（覆盖升级不丢配对的前提就是它不变）；
② 包内三套内容物一一对应，差的只是编译环境的字节。**真机验收是在本机那份上做的**（红米、强制 32 位、2.5 GB），
所以严格说：这版公开出去的 APK 没有逐台实测过，跑的是同一条出包脚本与同一批门禁。
两个电脑端包体积与本机一致（架构判据在云端也过了：x64 包内 `0x8664`、arm64 包内 `0xAA64`）。

⚠ **0.5.3 的两个电脑端包重出过，上表是最终值**（WiX 把构建时间写进包体，每次重打包哈希必换）。
重出的原因值得记一句：安装包模板曾把"封进包里的 exe"路径写死成 x64 那条产物，
所以第一版 `arm64` 包里装的其实是 x64 的本体。现在的判据是把包里的本体解出来，
核它与刚编出的那份同哈希、且 PE 机器码与包自称的架构一致（x64 → `0x8664`，arm64 → `0xAA64`）。
手机端 APK 没重出：那轮修复都在电脑侧，APK 与上表那行仍是同一份字节。

## 当前线上版本 0.5.2 的校验值

本表就是 **Releases 页面上那两个文件**的校验值，下载后与下表比对即可。两个文件的来源不同，这里分开说：

- **`LinkX-0.5.2-x64.msi`**：从本表所在的提交构建。**安装向导改版**：① 安装位置页改成一行可编辑的
  路径框（照 LocalSend 的样子），原先那个几乎空着的大目录列表框删掉了 —— per-user 安装的目录树本来就
  只有一条，用户看到的是"这安装器不会挑文件夹"；② 许可协议页的「下一步」必须先勾选"我接受许可协议中的条款"
  才放行，没勾时按钮是灰的、点下去也不会跳页（此前只写了 `EnableCondition` 一行，"没勾"分支什么动作都不做，
  控件保持 MSI 默认的可点状态 —— 许可协议在流程上等于没有闸门）。体积 1048576 字节。
  安装目录里随附五份许可文件：本项目许可、第三方组件许可登记，以及上游移植件的许可全文、署名与改动声明。
- **`LinkX-0.5.2-release.apk`**：同一份源码构建。**多选发送**：系统文件选择器支持多选，另加"从相册选图"
  可一次挑多张；挑好的文件进「待发清单」，可逐条移除，整批顺序发出，一个失败不打断其余并逐条写明原因。
  安装包内附五份许可清单（`assets/licenses/`），「关于」页可逐份查看全文。
  ⚠ 这份包用**本机新生成的测试密钥**签名（旧机那把 `linkx-test.jks` 不在本机），
  与用户手上已装版本的签名不同，`adb install -r` 会被拒；要用旧密钥重签后才能覆盖安装而不丢配对。

自己从源码构建出来的哈希必然与本表不同（WiX 把打包时间写进产物，安卓的 `.so` 还编进了源码行号），那不代表你构建错了。

| 平台 | 文件 | 大小 (bytes) | SHA-256 |
|---|---|---|---|
| Windows | `LinkX-0.5.2-x64.msi` | 1,048,576 | `249266f2c3fd43bb5d5eab9df01d101bf9447b1b957548282efde91bae966a12` |
| Android | `LinkX-0.5.2-release.apk` | 2,420,287 | `529217a5575069859a101e6df904731cc357ca5291425e17e543c46b4cc71460` |


这一版两端都要同批升级：共享 Rust 层没动，但**许可协议页与安装位置页只影响电脑端**，
手机端的多选改动在 Kotlin 层，两端协议没有变化，单独升一端也能互通。
调试包（带 AI 控制面，只在本机自测用）不归档不分发，放在 `Release/Debug/`。
电脑端这份 MSI 的**安装向导是中文的**（此前是英文），装到一半看到的字应该和下表说的一致。
这一版起 MSI 会多注册一条 `linkx://`（HKCU，不需要管理员权限），它是电脑通知卡上那两颗按钮的
回话通道；卸载时一并回收。通知卡本身还要程序启动时给开始菜单快捷方式补一次应用身份，
所以**不勾「创建开始菜单快捷方式」就没有卡片，只有托盘气泡**（气泡上没有按钮）。

MSI 的哈希每次重打包都会变（WiX 把打包时间写进产物），它核对的是同一份文件，不是同一份代码；
APK 在同样输入下可复现（同一份源码重跑两次，字节一致，已实测）。但**共享 Rust 层哪怕只改注释，
release APK 的字节也会变** —— 源码行号会编进 `.so`，所以安卓哈希变了不代表手机端行为变了，
要看改动清单。APK 用测试密钥签名，正式分发需自行重签，重签后哈希会变。

## 校验一个包

当前版本的安装包不在仓库里（`Release/Windows/`、`Release/Android/` 是出包机器上的目录，克隆下来是空的），
所以核对的对象是**你从 Releases 页面下载到的那个文件**：

```powershell
Get-FileHash -Algorithm SHA256 "$env:USERPROFILE\Downloads\LinkX-0.5.2-x64.msi"
```

输出的哈希与上面那张表一致，才算拿到同一个文件。历史版本同理：核对值在
`Archive/v<版本>/*.sha256`，本体可以就从同一目录取，也可以从 Releases 页面下载（一个版本一条）。
